# Allen Obsidian Note System

当任务涉及 Allen 的 Obsidian 主库 `/Users/heytea/Documents/obsidian_note`，尤其是以下情况时必须使用本 skill：

- 帮他新建或整理 Obsidian 笔记
- 将研究结果落到 Obsidian
- 把聊天内容沉淀成长期知识
- 清洗 OneNote 导入内容、网页摘录、零散草稿
- 帮他设计目录、索引页、模板、归档策略

## 目标

不是写“好看”的笔记，而是确保后续 **真正可持续沿用**：
- 新内容不继续变乱
- 索引、知识、项目、素材四种笔记明确分开
- 旧内容能逐步被吸纳进稳定体系
- 未来助手写入风格保持一致

## Vault 与既有约束

- 主库路径：`/Users/heytea/Documents/obsidian_note`
- 历史约定的规范路径：`Codex工作台/Obsidian笔记写作规范.md`（若当前 Vault 中存在）
- 历史约定的长期方案路径：`Codex工作台/流程规范/Obsidian笔记体系方案（Allen版）.md`（若当前 Vault 中存在）
- 历史约定的模板目录：`Codex工作台/模板/`（若当前 Vault 中存在）

这些路径可能因库整理或迁移而不存在。写入前必须先检查当前 Vault 的真实结构；若文件缺失，不要卡住任务，也不要凭空重建整套规范。继续沿用本 skill 的 frontmatter/分类规则，并读取目标目录中 1-3 篇现存邻近笔记作为命名与正文风格依据。

## 默认体系

后续默认采用：

1. **PARA-lite 管目录**
2. **MOC / Hub 管主题入口**
3. **Evergreen 管核心知识沉淀**
4. **Raw Inbox 管未整理输入**

### PARA-lite 目录解释

- `00 Inbox/`：临时记录、待整理摘录、还没判断归属的内容
- `01 Projects/`：阶段性推进事项、项目上下文、任务拆解、复盘
- `02 Areas/`：长期主题领域
- `03 Resources/`：外部资料、课程摘录、网页剪藏、参考素材
- `99 Archive/`：旧方案、完成项目、历史导入、过期素材

### Allen 当前库的映射规则

不要粗暴重构全库，采用渐进映射：

- `ai-related/` 视作 `02 Areas/AI`
- `项目相关/` 视作 `01 Projects`
- `Codex工作台/` 视作 `02 Areas/自动化工作台`
- `ai-related/OneNote恢复/` 默认按待清洗资源处理，优先进入 `03 Resources/` 或 `99 Archive/` 的思路来整理
- 无法立即归类的新内容优先进入 `00 Inbox/`

## 写笔记前的强制判断

每次写入前先做下面的判断，不能跳过：

### Step 1：判断类型
只允许先归入这四类之一：

1. **索引型**：负责导航，典型是 Hub / MOC
2. **知识型**：一篇只回答一个问题，长期复用
3. **项目型**：服务推进，关注目标、进展、卡点、下一步
4. **素材型**：原始摘录、会议速记、文章保存、待清洗内容

如果还不能判断，就先当 **素材型** 放进 `00 Inbox/`。

### Step 2：判断归属目录
- 如果是稳定主题的核心内容，优先接入现有主题目录
- 如果只是收集资料，优先 `03 Resources/`
- 如果是模糊草稿，优先 `00 Inbox/`
- 如果是旧内容收纳，优先 `99 Archive/`

### Step 3：判断是否需要接入已有 MOC
只要该主题已经有 3 篇以上相关笔记，就应优先：
- 链接到已有索引页
- 或补建一个新的索引页


### 字段约束
- `title`：与文件标题一致
- `source`：原始来源；自建笔记写相对路径
- `author`：默认 `Allen`；若明确是助手整理可写 `笨笨` 或 `Allen`
- `published`：外部来源发布日期；无则留空
- `created`：创建日期
- `description`：一句话描述用途
- `tags`：少量稳定标签，优先英文小写
- `type`：使用受控集合
- `status`：使用受控集合

### type 受控集合
- `index`
- `note`
- `learning-note`
- `project`
- `workflow`
- `resource`
- `archive`

### status 受控集合
- `raw`
- `draft`
- `processed`
- `archived`

## 正文结构

除 `.excalidraw.md` 等特殊文件外，正文默认结构为：

```markdown

## 摘要

## 核心内容

```

## 四类笔记的写法

### A. 索引型（MOC / Hub）
适合：主题总览、导航页、学习地图。

要求：
- 不追求细讲定义
- 重点是“这个主题有哪些子笔记、先看什么、怎么跳转”
- 应明确给出 3 个以上相关链接（如果存在）

标题示例：
- `LLM总览`
- `AI工具索引`
- `投资研究地图`

### B. 知识型（Evergreen）
适合：概念、方法、判断、对比。

要求：
- 一篇只回答一个问题
- 用自己的话写“我的理解”
- 不要把项目推进和摘录混进来
- 优先命名成一个明确问题或判断，而不是“杂记”

坏标题：
- `AI杂记`
- `一些想法`
- `工具研究随手记`

好标题：
- `MCP解决的核心问题`
- `RAG为什么需要Rerank`
- `Claude Code 与 Codex 的差异`

### C. 项目型
适合：项目上下文、方案推进、阶段记录。

要求：
- 必须包含目标、当前进展、卡点、下一步
- 优先服务于推进，不强求知识化表达
- 可以链接到相关知识页，但不要替代知识页

### D. 素材型（Raw / Resource）
适合：剪藏文章、会议随手记、临时摘录、还没内化的内容。

要求：
- 明确这是 raw 内容，不要伪装成正式结论
- 必须写来源
- 必须写后续动作：转知识 / 并入索引 / 归档

## 强制规则

1. **新笔记先分类，再命名**
2. **正式知识笔记一篇只回答一个问题**
3. **每个稳定主题必须有入口页**
4. **OneNote 恢复内容默认先视作资源**
5. **每篇 processed 笔记尽量保留 2-5 个相关链接**
6. **不要再新建 `杂记`、`随手记`、`一些想法` 这类模糊标题**

## 推荐工作流

### 当用户让你“整理成 Obsidian 笔记”时

1. 先定位目标主题或现有目录
2. 读附近 1-3 篇笔记，确认命名与风格
3. 判断新内容属于四类中的哪一类
4. 选目录
5. 套 frontmatter
6. 按默认正文结构写
7. 至少补 2 个有效相关链接（若存在）
8. 如果是稳定主题且缺少入口页，补一个 MOC

### 当用户让你“探索更好的 Obsidian 笔记风格 / 学习好例子”时

不要只给抽象流派介绍，优先结合 Allen 当前主库落地成一篇 **风格参考页**。

推荐做法：
1. 先读现有规范与体系页，至少包括：
   - `Codex工作台/Obsidian笔记写作规范.md`
   - `Codex工作台/流程规范/Obsidian笔记体系方案（Allen版）.md`
2. 再读用户库里 1-3 个真实例子，优先选：
   - 主题索引页（MOC）
   - 项目推进页
   - 知识沉淀页
3. 输出时不要追求“大而全”的 PKM 理论综述，而是压缩成 4-6 种最实用风格：
   - MOC / Hub
   - Evergreen / 单点知识
   - Project Dashboard
   - Resource / Raw
   - SOP / Workflow
4. 每种风格都必须写清：
   - 它是什么
   - 适合什么场景
   - 为什么好用
   - 常见误用
   - 在 Allen 库里的可参考例子
5. 新建一篇 workflow 类型笔记，文件名可直接用：
   - `Codex工作台/Obsidian优秀笔记风格参考.md`
6. 如果合适，把这篇参考页回链到 `Obsidian笔记写作规范`，形成“先看风格、再看规范”的路径。

核心原则：Allen 要的不是漂亮理论，而是**为什么会乱、该学哪几种风格、以后怎么不继续乱**。

### 当用户让你把 Codex / Agent / CLI / OpenSpec 研究结果写进 Obsidian 时

这类内容默认视为 **workflow / knowledge-curation 混合笔记**，优先写入 `Codex工作台/`，除非用户明确指定别的目录。

当任务是“对比两个本地仓库 / 两套架构 / 原始版与后来版，并解释每个目录作用和流程”时，默认不要只写一篇长文。优先创建一个专题目录：

```text
Codex工作台/<topic>/
├─ 00-<topic>总览.md
├─ 01-<对象A>.md
├─ 02-<对象B>.md
└─ 03-<对比与使用流程>.md
```

写法要求：
- `00` 是 index / MOC，给一句话结论、阅读顺序、回链。
- `01/02` 分别解释对象定位、目录职责、对象模型、核心流程、常用命令。
- `03` 专门做对比表和“真实使用时怎么串起来”。
- 先基于本机真实文件、README、AGENTS、tests、CLI help 验证；不要把聊天摘要直接搬进 Obsidian。
- 写完后必须回读或列出文件，确认文件数、行数/大小和入口页存在。

### 当用户要建立求职 / 刷题 / LeetCode 进度表时

这类内容默认视为 **项目型笔记**，优先写入 `01 Projects/求职准备/`。如果目录不存在，可以创建该目录，不要放到泛泛的 Inbox。

推荐做法：
1. 先抓官方或稳定来源的题单数据，不要手抄记忆版题单；LeetCode Hot 100 可从力扣学习计划页 `__NEXT_DATA__` 提取 `planSubGroups`。
2. 表格必须同时保留国内版与国外版链接：
   - 国内：`https://leetcode.cn/problems/<titleSlug>/`
   - 国外：`https://leetcode.com/problems/<titleSlug>/`
3. 字段优先包括：题号、中文/英文题名、难度、国内版、国外版、核心标签、状态、首刷日期、复盘日期、笔记链接。
4. 如果用户说“按知识点分类”，既要有全量表，也要有按知识点分组的小表；先给知识点总览，方便规划刷题顺序。
5. 状态建议使用可直接手改的枚举：`⬜ 未开始`、`🟨 一刷中`、`✅ 已通过`、`🔁 需复盘`、`⭐ 模板题`。
6. 写入后回读验证：确认题数、分类数、文件行数，并在 Obsidian 主库 Git 仓库中提交/推送（如果当前库已有远端）。

### 当用户让你把一整套现成学习资料 / 目录放进 Obsidian 时

适用场景：用户已经有一个本地整理好的学习目录（例如按模块分文件夹、按 `01-`/`02-` 编号的文章笔记），希望你**原样落进 Obsidian 主库**，同时又能自然接入他当前库的主题结构。

### 当用户让你围绕一个主题批量建立“公司 / 机构 / 产品版图”专题时

适用场景：用户要求在 `ai-related/` 这类长期主题目录下，新建一个成体系的专题文件夹（例如公司谱系、顶级机构、产品版图、赛道地图），并希望你**先写一个核心对象，再继续扩展更多对象，最后可持续跟踪**。

推荐做法：
1. **优先接到现有主题目录下，而不是新起顶层**
   - 例如 AI 公司/机构研究默认接到 `ai-related/` 下面。
2. **新建带序号的主题文件夹**
   - 保持 Allen 库里已有的编号感，例如：`17-top firms/`。
   - 序号不必追求绝对完美，但要尽量与现有同级目录连续、清晰。
3. **先建 1 个总览页，再建对象页**
   - 总览页文件名优先用：`00-<主题>总览.md`
   - 对象页按 `01-公司名.md`、`02-公司名.md` 编号展开。
4. **对象页默认写法**
   - `## 摘要`：一句话概括这家公司/机构为什么值得关注
   - `## 核心内容`：定位、强项、为什么重要、与其他代表玩家差异、对 Allen 当前研究方向的价值
   - `## 可执行动作`
   - `## 相关链接`
5. **当对象数量变多时，补一页对比页**
   - 文件名可直接用：`<主题>对比：维度A、维度B、维度C.md`
   - 对比维度优先用 Allen 真正关心的维度，而不是空泛公司介绍。
   - 例如：模型、Agent、开发者生态、开源、科学 AI、企业落地。
6. **优先做“研究框架”，不是百科全书**
   - 目标不是把所有公司资料抄全，而是回答：
     - 这家公司为什么值得持续追
     - 我后面应该重点看它什么
     - 它和其他玩家有什么结构性差异
7. **尽量做官方来源 grounding，但不要被反爬卡死**
   - 能抓官方 about / company / product 页面时，就用它补一句来源说明。
   - 如果遇到 Cloudflare / 403 / 超时，不要卡住整个任务；改用稳定共识信息整理，并在笔记里明确写：
     - 官方页抓取不稳定
     - 本页采用稳定共识信息，避免写依赖临时页面的细节
8. **总览页要持续回链全部对象页和对比页**
   - 后续每补一批，都同步更新总览页，别让专题变成散页。
9. **如果用户要求同步 GitHub**
   - 整个专题作为一个批次提交，commit message 直接反映“新增专题 / 扩展专题”。

核心原则：**这类专题页首先是给 Allen 未来持续观察用的研究地图，不是一次性的公司简介合集。**

### 当用户让你在现有主题目录下“新开一个专题文件夹”时

适用场景：用户会说类似：
- “放到 `ai-related` 里新加一个文件夹吧”
- “你自己加一下序号”
- “先把这篇写进去，再自己扩展几篇相关的”

这类任务不要只新建一个孤立文件。默认按 **“专题目录 + 00 总览 + 用户指定锚点页 + 同级扩展页”** 的结构落地。

推荐做法：
1. **先读目标父目录的现有编号与命名风格**，再决定新目录编号；不要拍脑袋乱插。
2. **目录名优先短而稳**，例如：`17-top firms/`；避免临时会话式名字。
3. **先建一页 `00-<专题>总览.md`**，说明：
   - 为什么要看这个专题
   - 这一组笔记先包含哪些子页
   - 一个最实用的观察/比较框架
   - 后续还能继续补什么
4. **先写用户明确给出的核心锚点页**，不要跳过用户提供的主材料。
   - 例如用户先给了 DeepMind 长文，就先整理成 `01-Google DeepMind.md`
5. **再补 3-5 篇同级对照页**，优先选最值得长期跟踪的 peer companies / peer systems，而不是随便凑数。
6. **总览页必须回链到现有主题页**，避免新专题成为孤岛。
7. **如果用户同时要求同步 GitHub**，完成后直接按 Obsidian 主库 Git 仓库处理：检查状态、提交整个新目录、推送当前分支。

默认命名建议：
- 目录：`<序号>-<topic>/`
- 总览：`00-<topic>总览.md`
- 子页：`01-...md`、`02-...md`、`03-...md`

核心原则：**这种任务不是“写一篇笔记”，而是“在现有知识体系里长出一个新专题入口”。**

### 当用户让你“学习 / 探索一篇或一组文章”时

这是 Allen 明确偏好的流程，尤其适用于 Anthropic / Claude / Hermes / Codex / agent engineering 这类文章研究。

必须遵守以下顺序，**不要一上来直接写摘要**：

1. **先尽量完整抓取原文**
   - 先拿到尽可能完整的正文，而不是只看标题、导语或二手摘要。
   - 目标是先保真掌握原文结构，再做压缩。
2. **再整理成中英对照版**
   - 每个主要章节先保留英文原意，再给中文解释。
   - 如果全文太长，不必逐段硬翻，但至少按章节 / 主题块做保真中英对照提炼。
3. **专业词汇尽量保留英文**
   - 对 agent / runtime / orchestration / tool / memory / context / evaluation / tracing / deployment 等术语，优先保留英文，并用中文解释含义。
   - 不要为了“全中文”把术语翻坏。
4. **最后再做总结**
   - 总结必须建立在“原文已完整阅读 + 中英对照已整理”之后。
   - 目标是**不失真**，不是追求文风漂亮。

#### 推荐落笔结构

这类文章默认优先写成 `learning-note` 或 `note`，正文建议包含：
- 原文链接
- 推荐理由
- 阅读日期
- 阅读关注点
- 一句话总结
- 中英对照笔记（按章节）
- 最重要的 3 个观点
- 可以迁移到我自己工作流 / 产品里的点
- 仍然没想明白的问题
- 想继续延伸阅读的关键词
- 相关链接

#### 关键原则

- **先证据，后结论**：先抓全文，再总结。
- **先保真，后提炼**：不要为了快，把复杂论证提前压扁。
- **术语优先保留英文**：尤其是工程、agent、架构类文章。
- **总结放最后**：不要把“我的理解”写成替代原文的东西。

推荐做法：
1. **先看源目录结构**：确认是不是已经有稳定模块划分、编号命名、`README` / `_index` 一类入口文件。
2. **优先接入现有主题目录，不另起一套顶层体系**：
   - agent / assistant / Claude / Anthropic / Hermes / Codex 相关内容，优先考虑 `ai-related/16-agent-assistant/`。
   - 其他主题也应先判断能否落到现有 `ai-related/` 子目录，而不是机械塞到 `00 Inbox/`。
3. **如果源目录本身已经结构化良好，就保留原始模块结构与编号命名**：不要为了“统一风格”打散已有的 `01-Engineering`、`02-Research`、`01-文章名.md` 这类学习顺序。
4. **在导入目录内补一篇总览入口页**，文件名优先用：
   - `<主题> 学习总览.md`
   这篇页负责说明：
   - 这套资料是做什么的
   - 建议学习顺序
   - 各模块各自适合什么时候看
   - 可以如何做阅读笔记
5. **总览页要回链到当前库里已有的相关主题页**，例如同类 agent / workflow / runtime 笔记，避免新资料成为孤岛。
6. **如果用户同时要求同步 GitHub**，并且 Obsidian 主库本身就是 Git 仓库，则在写入完成后继续：
   - 检查 `git status`
   - 提交新增目录
   - 推送到当前分支对应远端
   但汇报时要明确：这是“Obsidian 主库同步到了 GitHub”，不是单独给学习资料新建仓库。

核心原则：**已有结构好的学习资料，导入 Obsidian 时优先“平滑接入现有知识体系”，而不是重写成另一套新目录。**

推荐写法：
1. 先判断它是不是“明天要复习”的学习笔记；如果是，优先合并成 **一篇可连续阅读的总结页**，不要拆成很多零散短笔记。
2. 文件名优先使用清晰主题名，例如：
   - `Codex规范落点与常用命令学习笔记.md`
   - `Codex hooks 最小可用模板.md`
   - `Codex CLI 命令速查.md`
3. 正文结构默认保留：
   - `## 摘要`
   - `## 核心内容`
   - `## 可执行动作`
   - `## 相关链接`
4. 如果内容包含命令、能力对比、落点建议，优先用 **表格** 压缩，而不是大段散文。
5. 如果同时包含“官方结论”和“本机验证结果”，要明确分开写：
   - 官方事实：写来源链接
   - 本机现状：单列一节说明当前机器上的实际验证结果
6. 如果本机验证里发现 CLI / 工具当前不可用，不要把它写成长期规则；只把它作为这篇笔记里的“当前机器现状提醒”。
7. 相关链接优先回链到：
   - `[[Codex启动加载顺序]]`
   - `[[Codex Agent 能力与读取链路图]]`
   - `[[Obsidian笔记写作规范]]`
   - 同主题的 Codex工作台已有笔记

#### Hermes 专题补充规则

当用户要求研究 **Hermes Agent 自身**（位置、能力、架构、进化机制、当前启用状态）并写入 Obsidian 时，默认按 **“官方架构 + 本机实况” 双线结构** 落笔：

1. **先写本机事实**：优先落清楚可执行入口、安装路径、配置路径、记忆路径、skills 路径、sessions 路径。
2. **再写当前能力盘点**：版本、默认模型/provider、已启用 toolset、MCP、gateway、cron、skills 数量、delegation / memory / session_search / computer_use 等关键能力。
3. **再写官方架构理解**：从 Hermes 官方文档提炼统一核心（AIAgent）、prompt 组装、工具注册表、session 持久化、gateway、cron、plugin / MCP 等结构，不要只抄目录。
4. **明确区分“本机验证”与“架构认知”**，避免把某台机器当前配置误写成 Hermes 的长期通用规则。
5. **文件名优先使用“学习笔记 / 架构学习 / 能力盘点”类命名**，让它适合后续复习，而不是像一次性排障记录。
6. **结尾要补“当前还能继续进化的方向”**，例如：补 MCP、补 gateway、补 skill 体系、补架构图、补跨平台流水线。

核心原则：Allen 要的是 **明天能快速复习、以后能持续接着学** 的笔记，不是一次性聊天记录搬运。

### 当用户让你“帮我整理乱掉的笔记”时

优先做：
1. 把未整理内容集中进 `00 Inbox/` 或 `03 Resources/`
2. 把成熟内容升级为知识页
3. 给高频主题建立索引页
4. 对历史导入内容标记 `raw` / `archived`

### 当内容来自 OneNote / 网页导入时

不要直接当正式知识落库。
应优先：
- 保留原始内容为资源
- 提炼新知识页
- 从资源页链接到知识页

### 当用户让你“先盘点 / 清理 OneNote恢复目录”时

不要一上来搬文件。先做 **第一轮审计**：

1. 枚举目标目录下的 `.md` 文件数量。
2. 统计 frontmatter 中的 `status`、`recovery_quality`、`category` 分布。
3. 抽样读取：
   - 1 篇索引页
   - 2-3 篇 `processed/usable`
   - 2-3 篇 `raw/empty` 或 `thin`
4. 将结果分成三类：
   - **可直接吸收进正式主题体系**：已有正式承接页或明显可升级为 evergreen
   - **待补全 / 保留 raw**：只恢复到标题、正文过薄、需要回看 OneNote 原文
   - **保留归档**：时效性强、已被正式页承接、或只适合作为历史恢复记录
5. 新建一篇 **项目型清单** 到 `01 Projects/Obsidian整理/`，文件名建议：
   - `OneNote恢复-<主题>-第一轮整理清单.md`
6. 在原恢复目录的索引页里补一个链接，指向这份整理清单。

#### OneNote恢复 目录的默认判断规则

- `processed + usable`：优先判断是否并入正式主题页
- `raw + empty`：默认继续保留 raw，不立即升级
- `raw + thin`：优先合并同主题薄页，再决定是否归档
- `archived`：如果已经有正式承接页，通常保持归档，不要再恢复成主线知识
- `needs-verification`：默认视为资源，不直接当 evergreen

#### 输出时必须给 Allen 的结论

- 总量和质量分布
- 哪些内容值得先并入正式体系
- 哪些内容只该保留为 raw / archive
- 推荐的实际清理顺序（先易后难）

## 不该做的事

- 不要给所有笔记套同一种写法
- 不要把素材笔记伪装成 processed 知识笔记
- 不要为了图谱好看乱加链接
- 不要用复杂 Dataview 体系替代基本分类
- 不要一次性大规模搬家破坏 Allen 已有路径稳定性
