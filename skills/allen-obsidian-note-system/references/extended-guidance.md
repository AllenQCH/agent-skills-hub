### 当用户让你“学习 / 探索一篇或一组文章”时

这是 Allen 明确偏好的流程，尤其适用于 Anthropic / Claude / Hermes / Codex / agent engineering 这类文章研究。

必须遵守以下顺序，**不要一上来直接写摘要**：

1. **先尽量完整抓取原文**
   - 先拿到尽可能完整的正文，而不是只看标题、导语或二手摘要。
   - 目标是先保真掌握原文结构，再做压缩。
2. **再整理成中英对照版**
   - 每个主要章节先保留英文原意，再给中文解释。
   - 如果全文太长，不必逐段硬翻，但至少按章节 / 主题块做保真中英对照提炼。
3. **专业词汇尽量保留英文**
   - 对 agent / runtime / orchestration / tool / memory / context / evaluation / tracing / deployment 等术语，优先保留英文，并用中文解释含义。
   - 不要为了“全中文”把术语翻坏。
4. **最后再做总结**
   - 总结必须建立在“原文已完整阅读 + 中英对照已整理”之后。
   - 目标是**不失真**，不是追求文风漂亮。

#### 推荐落笔结构

这类文章默认优先写成 `learning-note` 或 `note`，正文建议包含：
- 原文链接
- 推荐理由
- 阅读日期
- 阅读关注点
- 一句话总结
- 中英对照笔记（按章节）
- 最重要的 3 个观点
- 可以迁移到我自己工作流 / 产品里的点
- 仍然没想明白的问题
- 想继续延伸阅读的关键词
- 相关链接

#### 关键原则

- **先证据，后结论**：先抓全文，再总结。
- **先保真，后提炼**：不要为了快，把复杂论证提前压扁。
- **术语优先保留英文**：尤其是工程、agent、架构类文章。
- **总结放最后**：不要把“我的理解”写成替代原文的东西。

推荐做法：
1. **先看源目录结构**：确认是不是已经有稳定模块划分、编号命名、`README` / `_index` 一类入口文件。
2. **优先接入现有主题目录，不另起一套顶层体系**：
   - agent / assistant / Claude / Anthropic / Hermes / Codex 相关内容，优先考虑 `ai-related/16-agent-assistant/`。
   - 其他主题也应先判断能否落到现有 `ai-related/` 子目录，而不是机械塞到 `00 Inbox/`。
3. **如果源目录本身已经结构化良好，就保留原始模块结构与编号命名**：不要为了“统一风格”打散已有的 `01-Engineering`、`02-Research`、`01-文章名.md` 这类学习顺序。
4. **在导入目录内补一篇总览入口页**，文件名优先用：
   - `<主题> 学习总览.md`
   这篇页负责说明：
   - 这套资料是做什么的
   - 建议学习顺序
   - 各模块各自适合什么时候看
   - 可以如何做阅读笔记
5. **总览页要回链到当前库里已有的相关主题页**，例如同类 agent / workflow / runtime 笔记，避免新资料成为孤岛。
6. **如果用户同时要求同步 GitHub**，并且 Obsidian 主库本身就是 Git 仓库，则在写入完成后继续：
   - 检查 `git status`
   - 提交新增目录
   - 推送到当前分支对应远端
   但汇报时要明确：这是“Obsidian 主库同步到了 GitHub”，不是单独给学习资料新建仓库。

核心原则：**已有结构好的学习资料，导入 Obsidian 时优先“平滑接入现有知识体系”，而不是重写成另一套新目录。**

推荐写法：
1. 先判断它是不是“明天要复习”的学习笔记；如果是，优先合并成 **一篇可连续阅读的总结页**，不要拆成很多零散短笔记。
2. 文件名优先使用清晰主题名，例如：
   - `Codex规范落点与常用命令学习笔记.md`
   - `Codex hooks 最小可用模板.md`
   - `Codex CLI 命令速查.md`
3. 正文结构默认保留：
   - `## 摘要`
   - `## 核心内容`
   - `## 可执行动作`
   - `## 相关链接`
4. 如果内容包含命令、能力对比、落点建议，优先用 **表格** 压缩，而不是大段散文。
5. 如果同时包含“官方结论”和“本机验证结果”，要明确分开写：
   - 官方事实：写来源链接
   - 本机现状：单列一节说明当前机器上的实际验证结果
6. 如果本机验证里发现 CLI / 工具当前不可用，不要把它写成长期规则；只把它作为这篇笔记里的“当前机器现状提醒”。
7. 相关链接优先回链到：
   - `[[Codex启动加载顺序]]`
   - `[[Codex Agent 能力与读取链路图]]`
   - `[[Obsidian笔记写作规范]]`
   - 同主题的 Codex工作台已有笔记

#### Hermes 专题补充规则

当用户要求研究 **Hermes Agent 自身**（位置、能力、架构、进化机制、当前启用状态）并写入 Obsidian 时，默认按 **“官方架构 + 本机实况” 双线结构** 落笔：

1. **先写本机事实**：优先落清楚可执行入口、安装路径、配置路径、记忆路径、skills 路径、sessions 路径。
2. **再写当前能力盘点**：版本、默认模型/provider、已启用 toolset、MCP、gateway、cron、skills 数量、delegation / memory / session_search / computer_use 等关键能力。
3. **再写官方架构理解**：从 Hermes 官方文档提炼统一核心（AIAgent）、prompt 组装、工具注册表、session 持久化、gateway、cron、plugin / MCP 等结构，不要只抄目录。
4. **明确区分“本机验证”与“架构认知”**，避免把某台机器当前配置误写成 Hermes 的长期通用规则。
5. **文件名优先使用“学习笔记 / 架构学习 / 能力盘点”类命名**，让它适合后续复习，而不是像一次性排障记录。
6. **结尾要补“当前还能继续进化的方向”**，例如：补 MCP、补 gateway、补 skill 体系、补架构图、补跨平台流水线。

核心原则：Allen 要的是 **明天能快速复习、以后能持续接着学** 的笔记，不是一次性聊天记录搬运。

### 当用户让你“帮我整理乱掉的笔记”时

优先做：
1. 把未整理内容集中进 `00 Inbox/` 或 `03 Resources/`
2. 把成熟内容升级为知识页
3. 给高频主题建立索引页
4. 对历史导入内容标记 `raw` / `archived`

### 当内容来自 OneNote / 网页导入时

不要直接当正式知识落库。
应优先：
- 保留原始内容为资源
- 提炼新知识页
- 从资源页链接到知识页

### 当用户让你“先盘点 / 清理 OneNote恢复目录”时

不要一上来搬文件。先做 **第一轮审计**：

1. 枚举目标目录下的 `.md` 文件数量。
2. 统计 frontmatter 中的 `status`、`recovery_quality`、`category` 分布。
3. 抽样读取：
   - 1 篇索引页
   - 2-3 篇 `processed/usable`
   - 2-3 篇 `raw/empty` 或 `thin`
4. 将结果分成三类：
   - **可直接吸收进正式主题体系**：已有正式承接页或明显可升级为 evergreen
   - **待补全 / 保留 raw**：只恢复到标题、正文过薄、需要回看 OneNote 原文
   - **保留归档**：时效性强、已被正式页承接、或只适合作为历史恢复记录
5. 新建一篇 **项目型清单** 到 `01 Projects/Obsidian整理/`，文件名建议：
   - `OneNote恢复-<主题>-第一轮整理清单.md`
6. 在原恢复目录的索引页里补一个链接，指向这份整理清单。

#### OneNote恢复 目录的默认判断规则

- `processed + usable`：优先判断是否并入正式主题页
- `raw + empty`：默认继续保留 raw，不立即升级
- `raw + thin`：优先合并同主题薄页，再决定是否归档
- `archived`：如果已经有正式承接页，通常保持归档，不要再恢复成主线知识
- `needs-verification`：默认视为资源，不直接当 evergreen

#### 输出时必须给 Allen 的结论

- 总量和质量分布
- 哪些内容值得先并入正式体系
- 哪些内容只该保留为 raw / archive
- 推荐的实际清理顺序（先易后难）

## 不该做的事

- 不要给所有笔记套同一种写法
- 不要把素材笔记伪装成 processed 知识笔记
- 不要为了图谱好看乱加链接
- 不要用复杂 Dataview 体系替代基本分类
- 不要一次性大规模搬家破坏 Allen 已有路径稳定性

## 完成后回报

向 Allen 汇报时，优先说明：
- 采用了哪种笔记类型
- 写到了哪个目录
- 是否新建或接入了索引页
- 是否使用了现有模板
- 如果有历史内容未整理，建议下一步优先清理什么
