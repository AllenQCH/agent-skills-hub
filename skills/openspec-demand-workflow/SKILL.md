# OpenSpec Demand Workflow

## Overview

按“需求确认 -> 方案确认 -> 代码 diff 确认 -> 执行确认 -> 落库记录”的顺序推进需求。不要跳步。只要用户以“openspec”方式聊需求，或明确要求先分析、先给方案、先给 diff，再执行代码修改，就使用这套流程。

## Core Rules

- 先确认需求，再确认方案，再确认代码 diff，最后才真正改代码。
- 未经 human 明确同意，不要执行真实代码修改、分支创建、commit、push。
- 如果后续沟通与已确认方案冲突，退回“方案确认”步骤重新对齐。
- OpenSpec change 名必须先询问 human 的“需求号 + 需求内容”，不要自作主张命名。
- OpenSpec 内容必须使用中文。
- 不要把一份总 OpenSpec 复制到无关仓库；只在实际改动过的服务仓库中记录本服务的 OpenSpec。
- 每一步操作前，先说明“当前步骤、为什么做、会影响什么”，再执行命令或改文件。
- 需要人工复核时，展示 `git diff`、关键命令输出或文件内容，不只给摘要。
- 允许在 human 明确确认后 commit / push 特性分支。
- 禁止自行创建 MR/PR，禁止自行合并到 `master` 或其他主干分支，也禁止推动任何进入主干的流程。
- 合并、提 MR/PR、指定评审人、进入主干等动作必须由 human 或团队按内部流程处理。

## Workflow

### Step 1: 识别并触发

当用户出现以下任一信号时，立即使用本 Skill：

- 明确提到 `openspec`
- 说“先分析”“先给方案”“先不要改代码”
- 说“先给我看 diff，再决定要不要改”
- 说“先把需求梳理一下”“先确认分支和需求”

先做一句简短说明：

`我会按 OpenSpec 需求工作流推进，先确认需求号、需求名和分支基线，再给方案。`

## Step 2: 先问需求号、需求名、基线分支

必须先向 human 确认这些信息：

1. 需求号
2. 需求名
3. 从哪个分支拉取
4. 目标特性分支名

如果用户没给全，继续追问，直到拿齐。

OpenSpec change 名格式固定为：

`YYYY-MM-DD-需求号 需求内容`

例如：

`2026-04-15-p35_15078 收货物流信息优化（国内）`

分支规则：

- 分支名单独由 human 确认。不要默认把 OpenSpec change 名直接当成 git 分支名。
- 蓝鲸需求的可部署业务服务统一使用 `feature/<蓝鲸需求号>-<蓝鲸需求中文标题>`；中文标题取平台标题去掉前置需求号标签后的原文，不得缩写、改写或翻译，只允许替换 Git ref 禁止字符。
- 默认从主干分支拉取特性分支；如果项目主干是 `master`，必须先同步远程 `master`，再基于最新主干创建新分支。已有非规范需求分支需要迁移时，将旧分支 merge 到这个新分支并验证祖先关系。
- Maven 公共依赖仓库禁止创建或使用 `feature/<蓝鲸需求号>-<蓝鲸需求中文标题>`。创建或切换分支前，必须从本次受影响消费者的 `pom.xml` 或 effective POM 核实其实际依赖版本：版本一致时使用该版本对应的既有维护分支；版本不一致时使用受影响消费者中占多数的版本。分支名沿用依赖仓库已有版本分支约定（例如 `feature/1.0.1`），不得臆造前缀或版本；出现票数并列、无法确认版本、或对应版本分支不存在时，必须请 human 确认，禁止回退到蓝鲸需求分支。
- Gradle 公共依赖包不套用蓝鲸业务服务分支名；按项目规则或 human 确认使用版本分支、维护分支等目标分支。
- 公共依赖仓库已有临时需求分支改造时，将其 merge 回按上述规则选定的目标版本分支，并验证祖先关系。
- 创建或切换分支前，把来源分支、目标分支名、是否已同步远程主干发给 human 确认。

## Step 3: 反复确认需求与改造方案

在真正写代码前，先完成方案确认。

方案阶段必须覆盖：

- 当前链路和改动入口
- 会影响哪些服务
- 每个服务的改动点
- 兼容性影响
- 风险与边界
- 不做什么

如果是多仓库改动，明确列出涉及服务。

方案没有被 human 明确确认前，不进入代码 diff 阶段。

如果 human 修改了需求口径，重新输出方案，不要沿用旧结论。

## Step 4: 先给代码 diff，再确认

方案确认后，先给 human 看预期代码改动逻辑，再决定是否真正改代码。

这里的“代码 diff”可以是：

- 关键文件改动点
- 拟新增字段/方法/转换逻辑
- 简化版 diff 片段

这个阶段的目标是让 human 判断：

- 代码逻辑是否合理
- 改动边界是否合理
- 有没有偏离上一步方案

如果 human 对 diff 有异议：

- 先修正 diff 方案
- 如有必要，退回 Step 3 重新确认方案

未经 human 明确确认 diff，不要执行真实代码修改。

## Step 5: 获得执行授权后再真正改代码

只有当以下两项都成立时，才执行真实改动：

- 方案已确认
- 代码 diff 已确认

执行前，再询问一次 human 是否要继续执行：

- 是否开始真正改代码
- 是否创建分支
- 是否 commit / push

得到同意后再做：

- 新建或切换分支
- 真正修改代码
- 运行可行的验证
- 更新 OpenSpec
- commit
- push

验证规则：

- 按项目实际技术栈和项目规则选择验证命令。
- Java 项目优先使用项目声明的 JDK 版本；如果项目或 human 明确 Java 8，就用显式 `JAVA_HOME` 执行 Maven/Gradle 验证，不要默认使用当前 shell JDK。
- 验证失败时先定位根因，只做一次有依据的修复；仍失败则停止并说明阻塞点。

## OpenSpec Rules

### 1. 命名

OpenSpec change 名必须使用：

`YYYY-MM-DD-需求号 需求内容`

要求：

- 中文需求内容
- 日期使用实际创建日
- 需求号和需求内容都必须来自 human 明确确认

### 2. 放置位置

只在“实际改动过的服务仓库”中创建或更新 OpenSpec。

如果一次需求改动了多个服务：

- 每个服务都补一份本服务自己的 OpenSpec
- 不要只在一个总目录里写
- 不要在未改动的服务里硬塞 OpenSpec

### 3. 每个服务的 OpenSpec 至少包含什么

每个服务仓库中的 OpenSpec change 至少包含：

- `.openspec.yaml`
- `proposal.md`
- `design.md`
- `tasks.md`
- `specs/<service-scope>/spec.md`

### 4. OpenSpec 内部写什么

#### `proposal.md`

必须写：

- 为什么要改
- 本次需求涉及的全部服务清单
- 本服务改了什么
- 对本服务的影响

#### `design.md`

必须写：

- 本次需求涉及的全部服务清单
- 本服务在整条链路中的位置
- 这次为什么这样改
- 改动文件
- 回归关注点

#### `tasks.md`

必须写成可核对的 checklist，至少覆盖：

- 模型/接口改动
- 转换/存储改动
- 验证或回归点

#### `spec.md`

必须写成 OpenSpec 要求格式：

- `## ADDED Requirements`
- 或 `## MODIFIED Requirements`
- 每条 Requirement 正文必须包含 `MUST` 或 `SHALL`
- 每条 Requirement 下至少有一个 `#### Scenario:`

### 5. OpenSpec 内容边界

只记录“本服务真实改过的内容”。

不要把整个需求的大而全背景复制到每个服务里。每个服务 OpenSpec 只说明：

- 这次需求总共改了哪些服务
- 这个服务为什么要改
- 这个服务改了哪些文件
- 这个服务该怎么回归

### 6. 多服务需求的全量服务清单规则

如果一次需求改动了多个服务，则每个服务仓库中的 OpenSpec 都必须包含一份完全一致的“涉及服务清单”。

要求：

- 任意打开一个服务的 `proposal.md`，都能看到这次改动涉及的全部服务
- 任意打开一个服务的 `design.md`，都能看到这次改动涉及的全部服务
- 服务清单必须是全量清单，不能只写当前服务
- 服务清单更新时，所有已改服务中的 OpenSpec 都要同步更新

推荐写法：

`涉及服务`

- `service-a`
- `service-b`
- `service-c`

然后再单独写：

`当前服务改动`

- 当前仓库改动内容
- 当前仓库回归点

### 7. 轻量级 `openspec/*.md` 写法

如果项目使用轻量级 Markdown 规格文档，而不是完整 OpenSpec change 目录，则文件开头必须先写变更规格区，再写接口字段表或示例。

推荐结构：

```markdown
## Context

说明当前问题、入口、目标和明确的非目标。

## 分支名称

- 目标分支：`feature/example`
- 来源分支：从 `master` 拉取

## 涉及服务

- `service-a`
- `service-b`

## Decisions

1. 只写当前服务内部的实现决策或契约决策。

## Changed Files

- `src/main/java/...`

## Regression Focus

- 当前服务需要保护的行为。
```

规则：

- `涉及服务` 只写本次有代码改动的服务。
- 如果同一需求改动多个服务，每个服务文档中的 `涉及服务` 清单必须保持一致。
- `Decisions`、`Changed Files`、`Regression Focus` 只写当前服务内部内容，不替其他服务写决策或文件。
- `分支名称` 必须写目标分支和来源分支，方便复盘。
- 当同一个文件也承担接口文档职责时，把详细请求/响应字段表放在上述变更规格区之后。

## Code Cleanup Boundary

- 修改代码时，可以删除本次改造引用链内暴露出的无效代码，例如无用 import、明显不可达分支或已失效的局部辅助逻辑。
- 清理范围必须限制在当前服务、本次触碰的调用链或引用链内。
- 不做跨模块、跨服务、无关文件的泛化清理。

## Execution Checklist

在一次完整需求中，按下面顺序检查：

- [ ] 已识别这是 OpenSpec 协作需求
- [ ] 已确认需求号
- [ ] 已确认需求名
- [ ] 已确认基线分支
- [ ] 已确认目标特性分支名
- [ ] 已同步远程主干后再创建特性分支
- [ ] 已确认 OpenSpec change 名
- [ ] 已给出并确认方案
- [ ] 已给出并确认代码 diff
- [ ] 已再次征求 human 是否执行
- [ ] 已真正改代码
- [ ] 已补齐所有实际改动服务的 OpenSpec
- [ ] 已运行符合项目 JDK/技术栈的验证命令
- [ ] 已展示最终 diff 供 human 复核
- [ ] 已征求 human 是否执行 commit / push

## Guardrails

- 不要在需求未确认时抢先写代码。
- 不要在 diff 未确认时直接提交实现。
- 不要把 OpenSpec 写成抽象空话，必须能支撑后续回归。
- 不要把未改动的服务写进“已改服务”清单。
- 不要遗漏 human 明确要求的命名规范和分支确认步骤。
- 不要自行创建 MR/PR。
- 不要自行合并或推动任何进入 `master` / 主干分支的流程。
- 不要把无关清理混入需求 diff。
